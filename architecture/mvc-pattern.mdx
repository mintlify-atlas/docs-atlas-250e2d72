UDA-generated projects implement the Model-View-Controller pattern using Spring MVC for the backend and RUP components (built on jQuery) for the client-side view layer. The two halves communicate exclusively through Ajax and JSON, enabling a Rich Internet Application (RIA) experience without a separate frontend framework.

## Spring MVC wiring

When udaPlugin generates a project, it configures Spring MVC's `DispatcherServlet` in `web.xml` and registers the required infrastructure beans in the Spring application context:

- `InternalResourceViewResolver` — resolves controller return values like `"entity/entity"` to `/WEB-INF/views/entity/entity.jsp`
- `Jackson ObjectMapper` — serialises Java objects to JSON for `@ResponseBody` methods
- `HandlerExceptionResolver` — maps exceptions thrown by controllers to structured JSON error responses
- Spring Security filter chain with udaHdiv integration for CSRF/XSS protection

<Note>
  All of this configuration is generated by udaPlugin and placed in `myapp-war/src/main/webapp/WEB-INF/`. Developers rarely need to modify it.
</Note>

## Controller conventions

### URL mapping

Generated controllers use a resource-based URL convention. Each controller is mapped to a root path corresponding to its entity, and individual operations use sub-paths.

```java URL mapping conventions
@Controller
@RequestMapping("/entity")        // root path: /myapp/entity
public class EntityController extends BaseController {

    @RequestMapping(method = RequestMethod.GET)
    public String index(Model model) { ... }           // GET  /entity

    @RequestMapping(value = "/search",
                    method = RequestMethod.GET)
    @ResponseBody
    public DataTablesOutput<EntityDto> search(...) {}  // GET  /entity/search

    @RequestMapping(value = "/{id}",
                    method = RequestMethod.GET)
    @ResponseBody
    public EntityDto get(@PathVariable Long id) {}     // GET  /entity/{id}

    @RequestMapping(value = "",
                    method = RequestMethod.POST)
    @ResponseBody
    public EntityDto create(@RequestBody EntityDto dto) {}  // POST /entity

    @RequestMapping(value = "/{id}",
                    method = RequestMethod.PUT)
    @ResponseBody
    public EntityDto update(@PathVariable Long id,
                            @RequestBody EntityDto dto) {}  // PUT  /entity/{id}

    @RequestMapping(value = "/{id}",
                    method = RequestMethod.DELETE)
    @ResponseBody
    public void delete(@PathVariable Long id) {}       // DELETE /entity/{id}
}
```

### REST vs. non-REST endpoints

UDA distinguishes between two types of controller methods:

| Type | Returns | When to use |
|---|---|---|
| View methods | `String` (view name) | Initial page load — renders a JSP |
| REST methods | `@ResponseBody` object | Ajax calls from RUP components — returns JSON |

The `index` method always returns a view name. All CRUD operations return `@ResponseBody` responses consumed by RUP components via Ajax.

## View conventions

### JSP views with RUP component tags

Each entity gets a single JSP file that declares the RUP components for that entity's maintenance screen. The JSP itself contains minimal logic—all dynamic behaviour is delegated to the RUP JavaScript components.

```jsp views/entity/entity.jsp — typical maintenance view structure
<%@ page contentType="text/html; charset=UTF-8" pageEncoding="UTF-8" %>
<%@ taglib prefix="c"      uri="http://java.sun.com/jsp/jstl/core" %>
<%@ taglib prefix="spring" uri="http://www.springframework.org/tags" %>
<%@ taglib prefix="form"   uri="http://www.springframework.org/tags/form" %>

<!-- Search form -->
<form id="entitySearchForm">
    <input type="text" id="name" name="name" />
    <button type="submit" id="searchButton">
        <spring:message code="button.search" />
    </button>
</form>

<!-- RUP table component — fetches data from /entity/search via Ajax -->
<table id="entityTable"></table>

<!-- RUP component initialisation -->
<script type="text/javascript">
    $("#entityTable").rup_table({
        url: "<c:url value='/entity/search'/>",
        formId: "entitySearchForm",
        columns: [
            { data: "id",          title: "ID" },
            { data: "name",        title: "Name" },
            { data: "description", title: "Description" }
        ],
        buttons: ["add", "edit", "delete", "refresh"]
    });
</script>
```

### TLD references

RUP components that require server-side tag support use a custom TLD. The TLD is distributed with udaRUP and declared in the WAR's `web.xml`.

## Model conventions

### DTOs vs. entities

UDA follows the practice of using separate Data Transfer Objects (DTOs) for the web layer rather than exposing JPA entities directly in JSON responses.

| Class | Used in | Purpose |
|---|---|---|
| `Entity.java` | Service and DAO layers | JPA-managed, never serialised directly |
| `EntityDto.java` | Controller `@ResponseBody` | Serialisation-safe, contains only the fields the UI needs |

Spring MVC's Jackson integration serialises DTOs automatically. Mapping between entities and DTOs is typically handled by a mapper class generated alongside the controller.

### Spring MVC Model

The `Model` object is used only in view-returning methods (initial page load). It carries data that the JSP needs to render the initial state of the page—reference data for select lists, page titles, user context, etc.

```java Model usage — only in view methods
@RequestMapping(method = RequestMethod.GET)
public String index(Model model) {
    model.addAttribute("pageTitle", messageSource.getMessage("entity.title", null, locale));
    model.addAttribute("statusList", entityService.findAllStatuses());
    return "entity/entity";
}
```

## The Ajax/RIA pattern

RUP components communicate with the Spring MVC backend exclusively through Ajax. The component library handles request construction, response parsing, error display, and UI state management. The developer configures the component with a URL and column definitions—the rest is automatic.

```
Browser (RUP component)
        │
        │  Ajax GET /entity/search?start=0&length=10&search[value]=foo
        ▼
Spring MVC DispatcherServlet
        │
        │  routes to EntityController.search()
        ▼
EntityController
        │
        │  delegates to EntityService.findAll(input)
        ▼
EntityService
        │
        │  delegates to EntityDao.findAll(input, EntityDto.class)
        ▼
EntityDao (Spring Data JPA)
        │
        │  executes SQL, maps result to List<EntityDto>
        ▼
        │  returns DataTablesOutput<EntityDto>
        │
        ◄─── JSON response ───────────────────────────────
```

## Complete request cycle

<Steps>
  <Step title="User interacts with the RUP table component">
    The user types in the search box and presses Enter, or clicks a column header to sort, or navigates to the next page. The RUP `rup_table` component captures the event and constructs a DataTables-compatible Ajax request with the current filter, sort, and pagination parameters.
  </Step>
  <Step title="Ajax request reaches the Spring MVC controller">
    The request arrives at `GET /entity/search`. Spring MVC routes it to the `search` method on `EntityController`. Spring's `HandlerMethodArgumentResolver` binds the DataTables request parameters into a `DataTablesInput` object and validates it with `@Valid`.
  </Step>
  <Step title="Controller delegates to the service">
    After validating the input, the controller calls `entityService.findAll(input)`. No business logic lives in the controller—it is purely responsible for HTTP concerns: parameter binding, validation, and response serialisation.
  </Step>
  <Step title="Service queries the DAO">
    The service passes the `DataTablesInput` to the DAO. Spring Data JPA translates the input's filters, sorts, and pagination into a SQL query. Results are mapped to `EntityDto` objects.
  </Step>
  <Step title="JSON response consumed by the RUP component">
    The controller returns a `DataTablesOutput<EntityDto>` object. Jackson serialises it to JSON. The RUP table component receives the response, updates the table rows, updates the pagination controls, and—if there are validation errors—displays them inline without a page reload.
  </Step>
</Steps>

## Search endpoint example

```java EntityController.java — search endpoint
@Controller
@RequestMapping("/entity")
public class EntityController extends BaseController {

    @Autowired
    private EntityService entityService;

    /**
     * Returns the initial JSP view for the entity maintenance screen.
     */
    @RequestMapping(method = RequestMethod.GET)
    public String index(Model model) {
        return "entity/entity";
    }

    /**
     * Ajax endpoint consumed by the RUP table component.
     * Returns a DataTables-compatible JSON envelope.
     */
    @RequestMapping(value = "/search", method = RequestMethod.GET)
    @ResponseBody
    public DataTablesOutput<EntityDto> search(
            @Valid DataTablesInput input,
            BindingResult bindingResult,
            Model model) {

        if (bindingResult.hasErrors()) {
            DataTablesOutput<EntityDto> output = new DataTablesOutput<>();
            output.setError(bindingResult.toString());
            return output;
        }

        return entityService.findAll(input);
    }
}
```

<Tip>
  The `DataTablesInput` / `DataTablesOutput` classes are provided by the `datatables-core` library, which udaLib includes as a transitive dependency. You do not need to add it manually to generated projects.
</Tip>

### DataTables JSON response structure

The RUP table component expects responses in the standard DataTables envelope format:

```json DataTables JSON response
{
  "draw": 1,
  "recordsTotal": 150,
  "recordsFiltered": 23,
  "data": [
    { "id": 1, "name": "Example entity", "description": "First result" },
    { "id": 2, "name": "Another entity", "description": "Second result" }
  ]
}
```

`DataTablesOutput<EntityDto>` serialises to this format automatically. The `recordsTotal` field reflects the total row count before filtering; `recordsFiltered` reflects the count after applying the current search terms—both are required for the RUP table's pagination controls to function correctly.

## Error handling

The `BaseController` registers a `@ExceptionHandler` that catches unhandled exceptions and returns a consistent JSON error structure. RUP components recognise this structure and display error messages to the user in a standardised feedback overlay, without requiring per-endpoint error handling code.

```java Error response structure returned by BaseController
{
  "code":    "INTERNAL_ERROR",
  "message": "An unexpected error occurred.",
  "details": "..."
}
```
